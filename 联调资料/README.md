## 命名与记录规则

1. 项目使用稳定简称，正式名称、别名和项目 ID 写入 `项目说明.md`；模块按职责命名，例如“建模雷达模块”“Java后端接口”“地感模块”。
2. 每个独立联调目标建立新批次。跨天继续同一目标可以沿用原批次；目标、协议基线或验证环境实质变化时另建批次并引用前一批次。
3. 每批只有一份正式完整报告，`00_联调记录与总结.docx`。Markdown 编辑源稿放在 `02_过程记录`，阶段小结作为过程材料保存。
4. 报告记录接口基线、角色及依赖、范围、实际过程、问题与修正、逐项结论、遗留项及退出情况。逐项注明真实双端、受控驱动、模拟依赖或组件测试，不能互相代替。
5. 按 A/B 角色、日期或阶段组织原始证据，保留请求 ID、试验 ID、原始报文、日志、journal、输入、模型、配置摘要、版本和退出证明。已失败的有效证据同样保留。
6. 原始证据不改正文。迁移前后核对字节数与 SHA-256；原位置、新位置、原文件时间和清理操作写入 `06_整理索引`。
7. 只有字节完全相同的静态工件才合并存储。不同阶段快照、不同长度日志及失败记录不按文件名当作重复。缓存等可再生成文件可以直接删除并登记。
8. 共享目录是交换和运行入口；最终资料以本目录为统一查阅入口。历史路径可保留目录联接或硬链接，入口不计作另一份完整数据副本。
9. 业务源码、原始权威接口文件和其他项目共用日志不移动；只收集本批次产生的工件，必要时复制引用并注明来源。账号、令牌、Webhook、DPAPI 文件不进入业务报告。
10. 结束时更新模块首页和 `项目索引.json`。后续 agent 从这里查找项目；不要再把新项目的正式记录散放在 `runtime` 根目录。

本规则适用于不同 AI 工具、App 或 CLI。使用 [_模板](_模板/README.md) 建立下一批记录；工具和业务程序版本按实际情况填写。

Markdown 源稿可用 `_管理工具/markdown_to_docx.py 源稿.md 输出.docx` 导出 Word，复用本机已有 Python 与 python-docx，不更改全局工具环境。
