# 公司内部推广与连接器重构方案

建议保留 Python 和现有联调逻辑，先用终端交互界面（TUI）统一启动入口，保留结构化日志和现有命令行供排障及自动化使用。先让两位首次使用的同事能独立完成接入，再扩到多人。当前 Java 联调继续使用现有连接器，重构从现有 Git 基线另开分支。

## 公司内部推广版联调流程

1. **首次部署，解压后双击一个脚本**

   两位同事各自在电脑上打开同一份工具包。脚本优先复用已有的 Python、钉钉和 Codex，缺少的组件补到工具目录。首次需要授权时，按网页提示操作并查看本机检查结果。已有可用的 Codex 登录或公司 API 配置直接沿用。

2. **发起人创建一轮联调**

   在启动窗口选择「创建联调」，选钉钉群、自己的工程和接入同事，再填一句本轮目标，例如「控制程序与 Java 测试环境验证 P001」。工具生成项目编号和邀请文件。邀请带入群、项目和参与人信息，账号、密钥和本机路径由各自管理。滑槽称做完后要换 Java，可以创建新联调，原有记录仍可打开查看。

3. **接入人导入邀请，工具匹配工程和 agent**

   同事从同一个启动窗口选择「加入联调」，导入邀请。工具先识别本机工程目录，再按目录匹配已有 agent。**如果目录识别失败，或者匹配结果不对，同事可以手动选目录，工具会重新匹配。** 同一目录有多个合适会话时，再由本人选一次。确认后，工具保存工程与会话的对应关系。

4. **工具自动检查两端能否接单**

   工具核对双方的群、机器人和项目会话，然后在后台发一条只读测试，等对方 agent 实际执行并回报。通过后，启动窗口或发起人的 agent 显示「联调就绪」。卡住时说明当前步骤及处理人，例如「请 B 端完成钉钉授权」或「任务已入队，等原会话处理完上一单」。首次授权网页用完即可关闭。

5. **发起人对自己的 agent 说「开始联调」**

   双方就绪后，由发起人说一句「开始联调」。两个 agent 按已登记的目标、允许操作和收尾时间自动派单、查结果并继续下一步，接入人保持工具在线即可。涉及部署、查看日志或验证前端时，使用本轮指定的测试环境和权限，按同一个任务号核对页面、Java 日志和控制程序结果。

6. **从同一个启动窗口继续上次联调**

   到设定时间后，工具保存进度、已发请求号和未决事项，再按规则收尾。第二天仍双击同一个脚本，首页可以直接选「继续上次联调」，看到项目名和上次停在哪一步。要找更早的项目，再选「最近联调」。创建、加入和继续联调都从这个窗口进入。

多人联调仍由一位发起人创建同一轮联调，邀请各负责方。每人完成本机工程、会话和真实接单验证后加入。发起人的 agent 统一派单和跟进依赖。首轮试点覆盖两端，随后用三台机器验证定向派单、角色分工、临时离线和重新加入。

## TUI 与滚动日志

TUI 更适合首次配置和日常看进度。日志适合还原故障、批量检查和交接。建议两者读取同一份任务状态和事件记录。

| 场景 | 当前滚动日志 | TUI 方案 |
| --- | --- | --- |
| 第一次使用 | 从输出里找授权或下一条命令 | 首页直接选创建、加入或继续，按实际缺项提示 |
| 联调进行中 | 综合多行日志判断对端在线和任务进度 | 固定显示当前项目、双方接入状态、最后回执、当前卡点和处理人 |
| 排障与留证 | 完整、易重定向，信息越多越难快速定位 | 先给短结论，按选中任务展开脱敏日志并打开完整文件 |
| 后台运行与自动化 | 适合无人值守和脚本采集 | 保留现有 CLI 和日志输出，TUI 可以退出，连接器由现有运行管理机制控制 |

首页优先放「继续上次联调」「创建联调」「加入联调」「最近联调」。每个项目页先显示这轮目标、当前阶段和下一步。工具状态至少区分已启动、钉钉已连接、任务已入队、agent 已处理和结果已回传，避免把 `ready` 当成业务验收。关闭界面与主动停连接器使用不同的操作。Textual 支持多屏切换和滚动日志组件。[Textual Screens](https://textual.textualize.io/guide/screens/) · [Textual RichLog](https://textual.textualize.io/widgets/rich_log/)

## 工程整理与兼容边界

目前根目录有 28 个 Python 文件，约 9700 行，含测试。`peer.py` 同时处理群消息、业务委派、历史恢复和 CLI。`setup_helper.py` 集中处理工具探测、身份校验、本地设置和会话登记。先按现有职责拆开这两处，再接入 TUI 和新流程。

- 将启动、授权配置、项目登记、Codex 会话、钉钉传输、任务与持久化、更新、打包和展示各放在职责明确的模块中。保留 `.cmd`、PowerShell 及现有 `peer.py` 命令作为过渡入口，逐步切到统一包入口。
- 继续使用个人 DWS 监听和群 Webhook 机器人。沿用实际发送者 ID 校验、独立连接器、现有工具优先和缺项只补到工具目录的做法。现有命令、消息格式、队列身份、回执和定时收尾以兼容用例保护。
- 读取旧配置、项目绑定和 SQLite 检查点。先用副本演练迁移与回退，验证同一项目、会话、队列消息和原请求号能够继续引用。连接中断或投递结果未知时，先查原回执再决定下一步。
- 建立明确的入口、依赖锁定、构建说明和 Windows 检查。在干净目录从源码按白名单生成发行包。回归覆盖中文路径、目录移动、重复启动、终端退出、授权过期、网关认证、CLI 能力差异和包内运行时。
- 更新或切换版本前保全已有状态，安排双机兼容检查。试点先验证原版本与新版本相互收发，再逐步统一版本。

把脚本归到根目录的 `scripts/`，按用途分类。用户日常仍从根目录的启动入口进入，入口只负责调用对应脚本，旧命令可在迁移期通过同样方式兼容。

| 子目录 | 放置内容 |
| --- | --- |
| `scripts/setup/` | 首次接入、工具探测和安装、授权配置 |
| `scripts/run/` | 启停、续接和运行管理 |
| `scripts/diagnostics/` | 接入检查、事件总线检查、现场诊断收集 |
| `scripts/release/` | 构建包、生成校验值、更新和发布 |

修改目录后一起验证各脚本的相对路径、发行白名单和解压后的启动入口。业务逻辑抽到 Python 模块，脚本主要处理入口参数和进程启动。日常构建的中间文件放在专用忽略目录，`dist/` 存放可用的发行包和对应校验值。确认新包已替代旧包后清理过时产物，当前交付、回退必需的包和联调证据按需保留。

## 语言选型

| 选项 | 对这个项目的收益 | 主要成本 | 建议 |
| --- | --- | --- | --- |
| Python + Textual | 复用现有进程控制、SQLite、认证、打包和测试，最快交付界面 | 发行包需要带或补齐 Python 运行时和 TUI 依赖，并验证 Windows 中文终端 | 作为本次重构方案。 [Textual 官方文档](https://textual.textualize.io/) |
| Go + Bubble Tea | 连接器主体可构建成 Windows 可执行文件，适合后续统一跨平台分发 | 迁移 SQLite、Windows 凭据、进程与文件锁、断线与更新逻辑，仍要调用 DWS 和 Codex | 等试点数据证实 Python 分发是主要障碍后，再用小样验证。 [Bubble Tea](https://github.com/charmbracelet/bubbletea) · [Go build](https://pkg.go.dev/cmd/go#hdr-Compile_packages_and_dependencies) |
| C#/.NET | 面向 Windows 的进程和凭据集成比较自然，可按平台发布为单文件 | 重写现有实现和大量回归，需验证打包体积及跨平台需求 | 公司明确长期以 Windows 和 .NET 为主时再评估。 [微软单文件发布文档](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview) |
| Rust + Ratatui | 终端渲染控制细，适合长期维护原生二进制工具 | 对现有流程、平台集成和发布验证而言迁移量大 | 先保留为可选方向。 [Ratatui 后端文档](https://ratatui.rs/concepts/backends/) |

短期遇到 Python 或终端兼容问题，先用试点记录复现条件。压缩发包、缩短首次启动时间和降低支持成本，都可以用这批数据判断是否值得换语言。

## 建议一并纳入的事项

- **邀请和身份核对。** 在确认页清楚显示将要加入的群、项目和对端。邀请可识别版本、重复导入和过期场景，仍以本人登录、群成员及真实机器人消息确认身份。支持重新选工程或重新绑定原会话。
- **一个入口、可恢复的失败。** 保留最近项目、上次断点和原任务号。提示应说明需要等、谁要做什么以及如何返回。日志可按任务查看和导出脱敏诊断，授权凭据始终留在本机。
- **权限和范围。** 给发起人一次确认目标、允许操作、测试机器及结束时间。只读接单通过后，涉及远程部署、数据库、日志或浏览器的检查各用已授权渠道。最终结果应区分真实应用处理、设备软件仿真和现场验收。
- **试点与发布。** 先由两位没用过工具的同事照说明独立完成接入，记录在哪一步需要人工解释。双端稳定后扩大到第三端。每次发行记录版本、对应提交、更新范围和回退方式。

## 工期估算

以下按 1 名熟悉现有工程的开发者估算，能约到对端协助双机验收。工期涵盖连接器推广与重构，公司业务接口、数据库历史处理、前端业务实现以及新增现场设备联调单独估算。

| 工作 | 人日 |
| --- | ---: |
| 对齐行为基线和 Windows 验证范围 | 1–2 |
| 拆分现有模块，保留 CLI 和协议兼容 | 4–6 |
| TUI 首页、创建和加入联调、目录与 agent 匹配及手动回退 | 5–8 |
| 近期项目、旧状态迁移、回退和诊断细化 | 3–5 |
| 两机验证、打包及新同事首次接入试点 | 4–6 |
| 试点反馈修正、发布检查和文档 | 4–7 |
| **两端推广版合计** | **21–34** |

按一人连续工作，约 **4–7 周**。完成前四项和最低限度双机验通后，可先出试点包。多人任务依赖、掉线与恢复验证另估 **5–9 人日**。如果同批改用 Go，再预留 **12–22 人日**用于迁移、兼容和双机回归。工期是规划估算，主要变数是旧状态迁移覆盖、Windows 认证环境差异和同事配合时间。

## Git 和实施顺序

以当前源码在 `main` 建立本地基线。源码、脚本、测试、配置示例、许可证和可复用的文档进入版本管理。个人授权配置、运行时、数据库、项目证据、工具缓存和发行包保留在原本机目录。公司远程仓库和发布权限由团队另行确定。

本次 Java 联调继续使用当前入口和已运行实例。开始重构时从基线创建 `refactor/connector-tui`，在独立工作区小步提交。先拆模块并跑现有回归，再接 TUI 和新流程，最后用原配置和原任务检查点验证可接续。双机试点核收后再合并和发布。
