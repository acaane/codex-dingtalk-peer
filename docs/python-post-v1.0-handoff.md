# Python v1.0 之后的改动与重构交接

2026-11-25。Python 维护线在 main，以 v1.0 为基线。独立的重构在 master。本文记录 Python 侧已经实现的行为、迁移时要保持的约束及验证入口。

## 首次配置和日常启动

- 初次运行 start.cmd，优先复用已安装的 Python、DWS 和 Codex。首次按提示完成身份、项目目录、机器人及必要的模型凭据配置。之后用同一入口启动，复用已有 DWS 登录、项目绑定和模型提供方，无需另开 Codex 前台窗口。
- setup_helper.py 的 prepare_local_codex 和 prepare_codex_startup 优先沿用已登记会话所在的 Codex 目录或本机保存的选择，再使用正常的 Codex 配置。连接器支持已有环境变量、Codex 自己的凭据来源和交互式补录。所需环境变量凭据可从本机终端取得或隐藏录入，Windows DPAPI 副本按目录、提供方、地址和变量名隔离，仅加载到启动进程及子进程。原用户配置和共享环境继续生效。
- start_connector 先检查现有实例。重复启动进入状态查看，原监听继续运行。首次设置或正常启动时，在身份通过且允许发送后只补缺失的更新策略。已有开关、发布端和自动发布设置继续生效。connector_update.py 保留已验证发布快照、真实机器人校验和旧版启动更新兼容逻辑。
- 需要重新配置时使用 scripts/setup/setup.cmd。现有一键启动流程见 [首次接入说明](participant-onboarding.txt)。

## 连续委派的截止与队列

- business_consumer.py 使用旧宿主启动请求限定连接、恢复前检查及空闲保活。验证当前项目、协调方、会话和完整原生队列后，已选中的委派使用自身存储的截止。后一张有效委派可以越过启动宿主的旧截止，前一张回合仍受其真实截止约束。
- 原生恢复可能自动启动回合。只有在其原始输入精确匹配本项目的任务文件路径和 SHA-256 时，宿主才将回合关联到该委派并采用其截止。未获得匹配时沿用原有有界行为。重构实现应优先保存队列 ID 与回合 ID 的原生关联，精确输入匹配可用于现有后端兼容。
- 延续既有持久去重。队列入队、唤醒、开始、回合完成与业务结果各有独立证据。回执未知时核实原记录。过期队列撤销仍限来源、绑定、队列 ID、截止和原文摘要都明确匹配的任务。真实业务回报由业务会话写文件，连接器转发。
- 本轮测试覆盖连续两单、后到回合跨过旧截止，自动接续的输入归属、旧期限拦截和既有的队列保护。入口为 tests/test_business_consumer.py、tests/test_instance_control.py、tests/test_setup.py 和 python -m unittest -v。新版本的实际双机验证留到对应联调窗口。

## Python 发布入口

将本次验证过的 Python 提交推进 main 后推送版本标签，例如 v1.0.1。工作流 .github/workflows/python-release.yml 从标签提交运行完整 Python 回归，按固定摘要准备 Windows 运行时，用原白名单打包，验证 ZIP 和解压后的离线运行时。构建成功后创建 Release 草稿，逐一核对 GitHub 接收的资产 SHA-256，再发布。旧 v1.0 的标签和附件仍由该基线发行保留。

版本发布包含源码 ZIP、Windows 完整 ZIP、连接器恢复包、DWS 事件诊断包及旧总线恢复包，每个 ZIP 有独立 .sha256 文件。运行时、已登录账号、私人凭据、项目 SQLite 及业务证据继续由各自本机管理。

重构对照优先使用 git diff v1.0..main、上述测试及当前协议实现。Rust 侧按自己的数据结构与发布入口承接等效行为。
